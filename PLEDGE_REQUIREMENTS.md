## V1 Implementation Assumptions

**Implementation Assumptions — Subject to Client Confirmation**

These assumptions are implementation decisions for V1 and can be revised after client feedback.

### Pledge record

- A Pledge is an independent transaction and references the existing Customer with deletion protection.
- Business Source is obtained through `Customer → Business Source`; no duplicate Business Source foreign key is added to Pledge.
- JMS generates a unique, immutable identifier in the format `PLG-` followed by an uppercase UUID hex value. The red `1305` is not used as the Pledge identifier.
- Pledge date is the date collateral is received and defaults to the current date in Nepal (`Asia/Kathmandu`). A supplied pledge date may be backdated.
- `लिएको रकम` is stored as the amount received/advanced, in NPR, with two decimal places and a non-negative value.
- Amount in words is derived from the numeric amount for future form output. It is not stored as duplicate data and is not included in this backend API phase.
- `साँवा ब्याज बुझाउने भाका: रु.` is represented as an optional `due_date` for V1. No interest amount or calculation is inferred from it.
- `due_date` cannot precede `pledge_date`; overdue is derived when an ACTIVE pledge's due date is before the current Nepal-local date.
- Red `1305` is treated as static preprinted form content, not generated or stored as a Pledge field.
- No general remarks, address, identity number, form number, or Customer snapshot fields are added in V1.

### Pledge items

- A Pledge is created through the API with at least one PledgeItem; multiple items are supported.
- PledgeItem contains an automatically assigned one-based sequence, a required description, weight in grams, and an integer quantity (`थान`) of at least 1.
- Weight is stored with three decimal places. Zero is accepted; negative weight is rejected.
- Quantity must be at least 1, enforced by model validation, serializer validation, and a database constraint.
- `जोड` is omitted because its meaning and calculation are not established.
- Material, purity, gross/stone/net weight, estimated value, and pledged value are omitted.
- When `items` is included in an update, it replaces the complete current item list, matching the existing nested Bill-item update convention.

### Lifecycle, validation, API, and scope

- The only stored statuses are ACTIVE, REDEEMED, and CANCELLED. New records start ACTIVE.
- Allowed transitions are ACTIVE → REDEEMED and ACTIVE → CANCELLED. Terminal pledges cannot be reopened or switched to the other terminal state.
- Redemption and cancellation dates are assigned automatically using the current Nepal-local date on the corresponding transition and cannot be supplied directly through the API. No transition history is stored.
- Closed (REDEEMED or CANCELLED) pledges cannot be edited through the update API.
- Due, redemption, and cancellation dates cannot precede the pledge date.
- The API is authenticated and provides list/create at `/api/pledges/` and retrieve/update at `/api/pledges/<id>/`. No hard-delete, repayment, accounting, reporting, or printing endpoints are added.
- Validation is enforced by both DRF serializers and model `save()` validation for the documented amount, item, date, and lifecycle rules. Database uniqueness constraints protect Pledge numbers and per-Pledge item sequence numbers.
- API list filters follow existing Bill conventions for customer, status, pledge date, date range, and text search.
- This phase does not implement amount-in-words generation, official-form output, frontend pages, interest, repayment, outstanding balances, accounting, or inventory.

## Phase 6 — Pledge Lifecycle Actions

The implementation scope supplied for Phase 6 is:

- Provide Redeem and Cancel actions for ACTIVE pledges using the existing authenticated status-update API.
- Ask for confirmation before submitting either action, explaining that the closed record cannot be edited or reopened.
- Display the status and redemption or cancellation date returned by the backend after a successful transition.
- Keep REDEEMED and CANCELLED pledges read-only, with no edit or lifecycle actions.
- Do not add repayment, interest, accounting, printing, or government forms. Use the existing backend contract; explain any API limitation before changing the backend.

Acceptance criteria:

- Declining confirmation sends no update. Confirming sends only `status: REDEEMED` or `status: CANCELLED` to `PATCH /api/pledges/<id>/` through the existing authenticated request utility.
- While a transition is pending, disable edit and both lifecycle actions and prevent duplicate submissions.
- On success, show the saved status and backend-assigned lifecycle date, and remove edit and lifecycle actions.
- On failure, show a safe error and reload the record when possible so a pledge closed by another session remains read-only.
- Existing list, create, detail, and edit behavior is preserved. No backend, database, or auth-utility changes are required for this scope.

## Phase 7 — Pledge Report
